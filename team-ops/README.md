# team-ops — שכבת האורקסטרציה של תמר

המקום שבו CEO (רוני) מדבר עם ראש צוות אחד — **תמר** — והיא מאצילה לסוכנים ומדווחת בחזרה.
זהו החצי של Cowork בארכיטקטורה. החצי של המוצר (מסך "דבר עם הצוות") יתחבר לכאן מאוחר יותר
דרך אותו `registry.json`.

## חוזה ההאצלה (6 שלבים)
1. **קלט יחיד** — רוני מדבר עם תמר בשפת החלטות ("אני רוצה X"). ערוצים: הצ'אט של Cowork, או מייל.
2. **פירוק** — תמר הופכת החלטה לפקודת עבודה (`work_order`) עם בעלים, תדירות ואילוצים.
3. **רישום** — כל פקודה נכתבת ל-`registry.json` (זה ה-registry היחיד — מקור האמת).
4. **ביצוע** — הסוכן הרלוונטי מבצע ומעדכן סטטוס + `activity_log`.
5. **דיווח** — תמר מסכמת לרוני. מיילים נשלחים כ**טיוטה** (המחבר לא שולח לבד).
6. **אסקלציה** — סוכן חסום → תמר מכינה מייל החלטה → סטטוס `awaiting_decision` עד שרוני עונה.

**קו ישיר:** רוני יכול לפנות ישירות לכל סוכן ספציפי; הסוכן עדיין רושם ב-registry כדי שלתמר תהיה נראות.

## סכמת פקודת עבודה (`work_order`)
- `id` — `wo-YYYYMMDD-NNN`
- `created_by` — `roni` | `tamar`
- `channel` — `cowork` | `email` | `product`
- `decision` — הבקשה בשפה חופשית
- `owner` — שם הסוכן
- `type` — `once` | `recurring`
- `cadence` — למשל `every_2_days` (ל-recurring)
- `next_due` — `YYYY-MM-DD` (ל-recurring)
- `constraints` — למשל `["no_shabbat"]`
- `status` — `new` → `assigned` → `in_progress` → `blocked` → `awaiting_decision` → `done`
- `questions_for_ceo` — שאלות ממתינות להכרעה
- `result` — תוצר / קישור
- `activity_log` — `[{at, by, note}]`

## כללים
- **לא בשבת** — אין שליחה/טיוטות ביום שבת. due שנופל בשבת נדחה לראשון.
- **מייל = טיוטה בלבד** — תמר מכינה טיוטה ל-roni@otegroup.co.il; רוני שולח.

## מי מפעיל את זה
משימת Cowork מתוזמנת **`tamar-dispatcher`** (יומי בבוקר) קוראת את ה-registry, מבצעת מה שבשל,
מכינה טיוטות מייל, ומעדכנת סטטוסים. ניתן לכוונן לתדירות גבוהה יותר (polling) בהמשך.

## מה נשאר לחיבור המוצר (החצי שרוני מדפלוי)
- תמר במוצר כותבת פקודות ל-`registry.json` (או ל-outbox שמסונכרן אליו).
- קריאה חזרה של סטטוסים/תוצרים מה-registry להצגה במסך.
